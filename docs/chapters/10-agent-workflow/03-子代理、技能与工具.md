# 03 子代理、技能与工具

> 本节回答"能力怎么扩展、任务怎么分工"：工具与技能的区别、什么时候派子代理、怎么让它们不互相打架。

## 本节目标

1. 说清工具（tools）与技能（skills）的区别，知道什么时候值得沉淀技能；
2. 会用三条判据决定是否派子代理；
3. 会规定子代理的输入与汇报格式，避免"合并时才发现对不上"；
4. 知道子代理的成本来自哪里。

## 先修

- 第 9 章 01 节（harness 五件套）、本章 01–02 节（AGENTS.md 与任务卡）。

## 3.1 技能与工具

| | 工具（tools） | 技能（skills） |
| ---- | ---- | ---- |
| 粒度 | 原子动作：读文件、写文件、跑命令、搜索 | 一组动作 + 领域知识的打包 |
| 例子 | `read`、`write`、`bash` | "按模板生成实验报告""批量处理 Excel" |
| 何时用 | 每次任务都会用到 | 某套流程你会重复做三遍以上、且步骤固定 |
| 谁来定义 | harness 提供 | 你（或团队）沉淀，写进项目或插件 |

沉淀技能的最小形式其实很简单：**一份模板文件 + AGENTS.md 里的一段说明**。等它稳定了，再考虑做成正式技能。

## 3.2 子代理：什么时候值得拆

![子代理分工](./images/subagent_split.png)

| 场景 | 是否拆 | 原因 |
| ---- | ---- | ---- |
| 先摸清陌生代码库，再决定怎么改 | 拆（探索代理） | 大量阅读会污染主上下文 |
| 三个互不依赖的模块同时改 | 拆（并行） | 省时间 |
| 关键结论需要第二双眼睛 | 拆（评审代理） | 专职找错，避免自我确认 |
| 改一个函数、加一行日志 | 不拆 | 派发与合并的开销比任务本身还大 |

> 记住：子代理不是"更强的模型"，而是**上下文隔离 + 角色分工**；每个子代理都会单独消耗 token。

## 3.3 派子代理的三条规矩

1. **给明确的输入边界**：探索代理只给目录与问题；评审代理只给 `src/` 与 `output/`，**不给你的解释**（否则它会顺着你的思路走）；
2. **规定汇报格式**：例如评审代理必须输出表格"问题 / 证据（文件:行）/ 建议修法 / 严重程度"，便于你逐条回应；
3. **主代理负责合并与验收**：子代理不直接改最终交付物，避免并发覆盖与责任不清。

## 3.4 工作流模板：探索 → 实现 → 评审

```text
【角色分工】
1) 探索代理：只读，输出"数据概况 + 3 条建模建议"，附证据（文件名/行号）。
2) 实现代理：按任务卡改代码，必须运行并贴输出。
3) 评审代理：只看 src/ 与 output/，输出 ≥3 条质疑（表格），不得修改文件。
【主代理】合并产物、逐条回应质疑、给出最终结论与局限。
【人】确认计划、检查 diff、签署结论。
```

## 3.5 成本提示

- 一个子代理 = 一份独立的上下文与模型调用；
- 并行三个子代理 ≈ 三倍 token；
- 小任务派子代理，往往比直接做更慢也更贵。

## 本节小结

1. 工具是原子动作，技能是打包的工作流；重复三次以上就该沉淀；
2. 只在"污染上下文、可并行、需评审"三类场景派子代理；
3. 输入边界与汇报格式要事先约定，合并与验收归主代理；
4. 子代理是真金白银的 token，先算账再拆。

## 思考题

1. 为什么评审代理不该拿到你的解释？
2. 什么情况下"两个子代理并行"反而会拖慢进度？
3. 你打算把哪套重复流程沉淀成技能？写出它的输入、输出与验收标准。

# 01 版本与时效管理

> 本节的定位：AI 工具迭代极快，教材写作基线是 dsh 0.1.5-rc.2，而官方在两周内就发布了多个版本。真正可迁移的能力，是**建立一套跟着版本走的工程习惯**。

## 本节目标

1. 会为 AI 工具建立"版本单一事实源"；
2. 会做版本巡检（npm dist-tags + GitHub Releases + 官方文档）；
3. 会写更新 SOP：发现新版本后按固定流程改文档、重验证、再提交；
4. 知道"时效标记"的作用：让过期内容可以被一次性找出来。

## 1.1 为什么需要版本管理

| 现象 | 后果 |
| ---- | ---- |
| 命令/参数随版本变化 | 学生照教材敲命令报错 |
| 界面与菜单调整 | 截图与步骤说明失效 |
| 模型名称与价格调整 | 成本估算失真 |

结论：**凡是"会变"的内容，都要有单一事实源 + 定期巡检 + 更新流程**，而不是靠记忆。

## 1.2 版本单一事实源

教材把版本信息集中在一个文件里：docs/build/dsh_version.yaml

| 字段 | 作用 |
| ---- | ---- |
| baseline.version / released_at / checked_at | 基线版本与核对日期 |
| baseline.node | Node.js 版本要求 |
| upstream.* | 官方仓库、文档站、Releases、定价页、开放平台链接 |
| watch.dist_tags | 需要盯的发布渠道（latest / next / alpha） |
| review_on_change | **一旦版本变化，必须复核的文件清单** |

> 要点：把"需要改哪些文件"写进事实源，更新时就不靠回忆。

## 1.3 版本巡检：三条命令 + 一个页面

| 手段 | 命令 / 入口 | 看什么 |
| ---- | ---- | ---- |
| npm 渠道 | npm view @deepseek-ai/dsh dist-tags | latest / next / alpha 各是什么版本 |
| GitHub 发布 | 仓库 Releases 页 | 每个版本的中文更新说明（含破坏性变更） |
| 本机版本 | dsh --version | 本机装的是哪个版本 |
| 官方文档 | 文档站 | 命令、界面、配置的最新说明 |

## 1.4 双周巡检与自动提醒

教材仓库用 GitHub Actions 做**双周巡检**（每月 1 日与 15 日）：.github/workflows/dsh-release-watch.yml

- 发现新版本 → 自动开 Issue（含更新 checklist）；
- 已存在同名开启中的 Issue → 不重复创建；
- 巡检报告作为 artifact 存档。

> 你也可以给自己用：把巡检命令写进日历提醒，或写一个本地脚本定期跑。

## 1.5 更新 SOP（八步）

1. 跑巡检脚本 check_dsh_release.py（或手工执行 1.3 的三条命令）；
2. 读 Release notes，标记**可能影响教材**的条目（命令、界面、模型、价格）；
3. 用"时效内容（基线"作为关键词，一次找出所有需要复核的段落；
4. 按 review_on_change 清单逐文件修改；
5. 更新 dsh_version.yaml（版本、核对日期、复核记录）；
6. 复核/重截受影响的截图（第 9 章 03 节那 4 张）；
7. 重跑构建与校验（validate_book / validate_code / check_indexes / check_pdf_layout）；
8. 提交并关闭巡检 Issue。

## 1.6 时效标记约定

正文里所有易变段落都以固定格式开头，例如：

> 时效内容（基线 v0.1.5-rc.2 / 2026-09-19）：本节涉及版本号、命令、界面与价格。

好处：**升级时只需一次 grep**，不必通读全书。

## 本节小结

1. 版本管理的三步：单一事实源、定期巡检、固定 SOP；
2. 把"要复核哪些文件"写进事实源，而不是记在脑子里；
3. 时效标记让过期内容可被一次性定位；
4. 这套机制不仅适用于教材，也适用于你自己的科研代码与工具链。
